    Mandatory identity verification, made into a step people understand.

    Many users dropped off at an identity verification (KYC) step that regulation made mandatory. Instead of removing the friction, the flow was redesigned so the reason, current status, and next action are always visible.

    Overview

    About the project

    Context and challenge
    In a mobile app in a regulated industry, people had to complete identity verification (KYC, Know Your Customer) before using the service. The step couldn’t be skipped, and many users dropped off right there.
    Rachel’s role
    • Led research, the status and exception logic of the verification flow, and UI design.
    • Co-owned the design system and handed components and states to engineering with annotations.
    Collaboration (public scope)
    Worked with a product owner, product manager, business analyst, and developers, applying one set of principles to two markets with different identity-verification regulations.
    Project type
    Previous-role project · Client and product names are not disclosed

    A project Rachel Cho delivered in a previous role. It covers only what can be shared publicly; screens and data are new examples created for illustration.

    Problem

    What stopped people wasn’t scanning an ID. It was not knowing why it was needed, where things stood, or what to do if it failed.

    Solution

    Explain why verification is needed up front, always show the current status, and offer one clear next action whenever something fails.

    Key decisions

    Key design decisions

    01

    Why, what triggered it, and how long—first.

    Before verification starts, the screen explains why it’s needed, which action triggered it, and how long it will take. Instead of listing every document option, it shows only the recommended path available now.

    What changed for users People start verifying after “Why do they need this?” has been answered.

    02

    Always show where things stand.

    Verification status is split into four states—not started, in review, approved, action required—and shown the same way on every screen. During the 30–60 seconds of processing, the wait time is stated so a quiet screen doesn’t feel like failure.

    What changed for users After submitting, people no longer wonder “Did it go through?”

    Recreated for illustration · Sample copy

    03

    Even on failure, one next step.

    Each failure message says what happened together with the one thing to do now. Blocking errors use red to stay distinct from warnings and guidance, and status is conveyed by wording and icons, not color alone.

    What changed for users Even when blocked, people continue to the next step instead of starting over.

    • You’re offline

      Says what to check, then offers a way back.

      Check connection and retry →

    • A temporary server problem

      Makes clear it isn’t the user’s fault.

      Try again shortly →

    • An account already exists

      Stops a duplicate account before it’s created.

      Sign in to your account →

    • Used the wrong email?

      Adds a way out where people could only resend the code.

      Change email →

    Results

    Results and lessons

    Measured and reported results

    • Usage metric+95%Successful verification completion
    • Usage metric+25%First-transaction completion after verification
    • Operations metric−25%Verification-related support inquiries

    Screens and flows that changed

    • An intro that gives the reason, trigger, and expected time before verification
    • Four verification states shown the same way on every screen
    • For each failure, what happened and one next action
    • A path to change a mistyped email
    • One set of principles applied to two markets with different regulations

    What I learned

    Friction that regulation requires often can’t be removed. The core principle of this project was that when people know the reason, the current status, and the next action, the same step becomes a process they can accept.

    Figures were measured and reported in the project after launch and reflect several design changes applied together. Screens are new examples created for illustration.
